Demo guide

Follow the work and the money

Every live inference call, including planning, source review, repairs, and synthesis, uses Katara Cortex and is paid through x402 from the wallet: native USDC on Avalanche C-Chain on Live, or test USDC on Avalanche Fuji on Test. Public source requests are free; a source that demands payment is marked unavailable.

The payment boundary

  1. Send the exact completion request without payment. The gateway responds with HTTP 402 and a payment challenge.
  2. Validate x402 v2 and keep the entries for the network's chain, token and Katara's settlement contract, the token signing domain, and the Katara Cortex model. Katara lists an upto (Permit2) entry first and an exact (EIP-3009) entry for the same maximum.
  3. Choose upto when the wallet's Permit2 allowance covers the quote or the quote offers eip2612GasSponsoring; otherwise choose exact.
  4. Reserve the maximum amount in the on-disk ledger before signing. Check the invocation cap, outstanding authorizations, and current wallet balance.
  5. Sign the fixed authorization locally and resend identical request bytes with PAYMENT-SIGNATURE. An upto signature is a Permit2 witness transfer of at most the quoted amount to the upto proxy, naming the settlement contract and the quote's facilitator; with sponsoring it carries an EIP-2612 permit for Permit2 of the same amount. An exact signature is an EIP-3009 transfer of the quoted amount. A 412 permit2_allowance_required answer to upto is paid again with exact on the same quote.
  6. Record the completion metadata and structured findings. A successful HTTP response leaves the payment pending until chain evidence establishes its charge.

The client uses the official x402 EVM SDK. Each call allows at most three signed challenge attempts. Unpaid quote requests are spaced to stay under Katara's limit of thirty a minute per address; a 429 quote_rate_limited answer to an unpaid request is retried after its Retry-After (one to sixty seconds, at most eight times), and a 429 that answers a payment is never retried with that payment. Gateway refusals keep their code, parameter and message in the call record, the report and the CLI output. Report links go to the explorer of the network each payment settled on. A timeout or fresh challenge never releases a previous authorization. The ledger uses atomic writes and a wallet process lock. Keep the wallet in one checkout and preserve its .katara directory while payments are outstanding.

Shared budget

Exposure = confirmed actual charges + maximum amounts of pending authorizations
Before signing: exposure + new maximum must be within the invocation cap

Reconciliation uses a finalized Avalanche block. An exact record is confirmed by a matching token AuthorizationUsed nonce, one x402 Settled event for the buyer, and a token debit minus refund equal to the actual settlement amount in the same successful receipt. An upto record is confirmed once its Permit2 nonce is used and the settlement contract has emitted one Permit2 Settled event for the quote's ticket and the buyer; until then its full maximum stays reserved, since the charge is pulled and attributed in separate transactions. An unused authorization expires only after its validity window has passed in finalized chain time. Missing RPC evidence keeps the reservation in place.

Katara publishes these addresses on its Networks page, and they appear in every payment challenge. The client fixes every value in this table. Addresses are per chain. On Avalanche C-Chain, 0x7f8D1049519Ddcb1Cb041Fb1b0dF7A125e96ACF3 is the Live settlement contract; on Fuji the same address belonged to the Test settlement contract until October 2026. The client checks each network's chain ID, so an address is only ever used on its own chain. The .env keys KATARA_SETTLEMENT_ADDRESS, KATARA_X402_ASSET, KATARA_CHAIN_ID, KATARA_X402_NETWORK, KATARA_GW_BASE and KATARA_GW_MODEL are optional; one that disagrees with the selected network stops the client. The doctor check compares the gateway's chain and settlement contract with these values and verifies deployed contract code, the settlement contract's token, the token signing domain, Permit2 and the upto proxy. The public Avalanche RPC rate limits busy addresses; the client retries an RPC 429 or 5xx up to five times with growing waits (or as Retry-After asks, when that is ten seconds or less), reuses balance, block and allowance reads for five seconds, and otherwise stops with rpc_http_<status>. Settlement searches read logs in pages of 2000 blocks and halve the page whenever the RPC refuses a range as too wide (the public C-Chain endpoint allows 100); they cover 200,000 blocks after each authorization at any page size. Another JSON-RPC refusal stops with rpc_error_<code> and the RPC's message. Set AVALANCHE_RPC_URL to your own HTTPS RPC endpoint for the network's chain to avoid that limit; Avalanche lists RPC providers on its integrations page. For Live runs this is the recommended setup. Only one payment with a sponsored Permit2 approval is in flight per wallet; other calls pay with exact until it settles or its deadline passes, because each sponsored permit takes the token's next nonce. Optional limits are KATARA_DEMO_CONCURRENCY (1–4), KATARA_DEMO_DEADLINE_SECONDS (30–3600, default 1800) for each example, KATARA_DEMO_MAX_TOKENS (128–2048), and KATARA_DEMO_SILENCE_SECONDS (15–300, default 60), the longest pause the client accepts within a reply. Replies are streamed, so a slow Katara Community model that keeps sending is never cut off. Katara sends nothing before the first token and allows a pay-per-call request about 210 seconds for it, so the client waits up to 240 seconds for a reply to start. PAYMENT-RESPONSE arrives with the stream's headers, before the charge is known; the closing chunk's katara object carries cost_usdc, which the call record keeps. A stream that Katara ends with an error chunk is not charged and stops the call with completion_stream_failed; one that stalls stops with response_silent, and its payment stays reserved until the chain settles or expires it. An explicit --budget is required for each paid run. Quotes determine the authorization amounts; Katara charges at least 0.025 USDC per call on both networks.

Test

Test is paid exactly like Live, with the same wallet, but in test USDC on Avalanche Fuji. Its ledger is separate from Live's. Test quotes offer no sponsored approval because the test token takes no EIP-2612 permit, so upto on Test needs the wallet's own Permit2 approval, which npm run faucet sends along with the daily claim. Without it, Test payments use exact. When no Fuji provider is free for Katara Cortex, the Test network answers with a simulated reply that runs no model but is quoted, paid and settled like any other. The client records the call as simulated and gives the agent its built-in fixture output, and the report counts the simulated calls above the answer. Test therefore proves the wallet, payments, ledger and reconciliation, not answer quality. Live refuses a simulated quote before signing and a simulated reply after it.

Master synopses

The master reviews child claims against their cited source spans, then writes a direct answer with scenario-specific sections. Unsupported or uncertain claims are excluded. A second source review checks the summary and each section. Rejected sections are replaced with supported findings or a missing-evidence statement. Review reasons, claim hashes, source-span hashes, call IDs, and the original draft remain available in the report.

Each review batch contains at most 12 items. At most four batches are attempted per review phase, with an eight-call limit for the master across planning, reviews, synthesis, and repairs. Oversized evidence or a failed review remains uncertain. Katara Cortex reviews and master synthesis allow 2,048 output tokens. This checks source support but does not prove factual correctness.

To revise an exported answer from recorded research, use npm run synopsis -- <run-id> all --budget 1.00 --total-cap 8.00, reconcile, then npm run synopsis:export -- <revision-id>. Both caps apply to the current wallet ledger. Matching ignored local source snapshots are required; truncated public excerpts cannot substitute for the source text. Revisions include their source-report hash, implementation hashes, review decisions, calls, and payments. They retain original run JSON and cannot turn an unreviewed draft into an approved answer during export.

Evidence files

Each run writes .katara/runs/<run-id>/<example>.html and matching JSON. The report contains the public command, executed tree, child findings, master result, source URLs and retrieval timestamps, source SHA-256 hashes, requested and served models, usage, authorization maxima, and confirmed transaction links. A dirty checkout is labeled with +uncommitted after its Git revision.

Source citations are checked for permitted source IDs and line bounds. Findings also undergo a source review before synthesis. Claims without source support are excluded; factual correctness still requires judgment. Repository links point to a fixed commit and original lines. Other line numbers refer to the extracted view inspected by agents. Source excerpts in exported reports are limited to 25 words each; hashes identify retrieved response bytes, but the report does not preserve a full snapshot of changing pages.

Report exports expand product references to Katara Cortex; payment identifiers and source hashes retain their recorded values. The report intentionally saves the public command and structured research findings. It does not export full model request/response transcripts, payment signatures, private keys, or complete source articles. Bounded source views are saved privately under .katara/runs/<run-id>/support/; revision drafts remain in .katara/synopses/. Preserve these local files for later review and keep them out of the public snapshot. Review generated findings and URLs before sharing a report. Offline reports carry an explicit synthetic-fixture banner and cannot establish live research or payment success.

Dependency updates and license

Run npm run audit alongside the offline checks. Dependabot checks npm weekly and groups security fixes separately; updates require review before merging. The code uses the MIT license. Source excerpts retain their original terms.
